Development roadmap

Linked List Game

Build a small, satisfying interactive diagram first. Add lessons only after moving nodes and rewiring pointers feels clear and reliable.

Guiding principles

  • Keep list rules separate from drawing and mouse interaction.
  • Finish one playable vertical slice before adding more data structures or levels.
  • Make invalid states visible and explainable instead of silently preventing them.
  • Prefer simple pointer lines and readable labels over visual effects for now.
01

Stabilize the application shell

Turn the current blank OpenGL window into a dependable place to build.

Focus: window, input, project organization

  • Create small Application, Window, and Input modules.
  • Track window size, mouse position, mouse buttons, and Escape-to-quit.
  • Set up a basic 2D coordinate system so UI positions are expressed in pixels.
  • Choose folders for model, rendering, and interaction code.

Done when: the window resizes correctly and displays the live mouse coordinates.

02

Model a linked list without graphics

Build the rules that the visual game will represent.

Focus: pure C++ data model and tests

  • Define a stable node ID, a value, and optional next and prev links.
  • Create a graph/list model that can add nodes, remove nodes, connect pointers, and disconnect pointers.
  • Validate invariants: valid IDs, one outgoing link per pointer slot, and no accidental dangling references.
  • Write unit tests for every edit operation and edge case.

Done when: list edits can be tested entirely without creating an OpenGL window.

03

Draw a static linked-list diagram

Make a fixed list understandable at a glance.

Focus: 2D shapes, text, and pointer lines

  • Render node cards containing a value area and labeled next / prev socket areas.
  • Draw directional lines between sockets, with arrowheads to show pointer direction.
  • Draw an explicit nullptr label for empty pointers.
  • Add labels for head, tail, and temporary algorithm pointers.

Done when: a hard-coded three-node list is legible without any instructions.

04

Make nodes movable

Let players arrange the diagram while preserving the list structure.

Focus: hit testing and drag interaction

  • Store a visual position for every node separately from its list data.
  • Detect which node card is under the mouse.
  • Drag a card while the mouse button is held and keep its pointer lines attached.
  • Clearly highlight the card currently being dragged.

Done when: every node can be repositioned and all links follow it smoothly.

05

Implement manual pointer rewiring

This is the core game mechanic: players create and break links themselves.

Focus: sockets, previews, and safe edits

  • Begin a link drag from a node's pointer output socket.
  • Show a temporary line from the source socket to the mouse.
  • Highlight compatible destination sockets while dragging.
  • Commit the model change only after a valid drop; allow dropping away from a node to set the pointer to nullptr.
  • Give clear visual feedback for invalid drops.

Done when: the player can turn A → B → C into A → C through direct manipulation.

06

Add a small sandbox

Provide a safe place to experiment before turning the interaction into lessons.

Focus: player tools and feedback

  • Add controls to create a node, delete a node, and reset the scene.
  • Display the current head and list length.
  • Show helpful errors, such as a disconnected head or an unreachable node.
  • Support undo for the latest pointer or node edit.

Done when: a player can build, break, inspect, and reset small lists without restarting the application.

07

Create the first teaching level

Teach one operation, not all operations at once.

Focus: guided insertion

  • Present a starting singly linked list and a target outcome.
  • Ask the player to insert a node after a chosen position.
  • Prompt for the valid range of k before edits begin.
  • Check the final graph against the target and explain mistakes in terms of pointers and edge cases.

Done when: someone unfamiliar with the code can complete one insertion puzzle and understand why the boundary range matters.

08

Expand deliberately

Only add scope after the first lesson is fun, stable, and understandable.

Possible next features

  • Traversal, deletion, reversal, and cycle-detection lessons.
  • Doubly linked lists and temporary pointers such as slow and fast.
  • Level definitions loaded from files instead of compiled into C++.
  • Polish: animations, sound, themes, node skins, and challenge scoring.

Done when: each new feature reinforces the same core interaction instead of introducing a separate system.

Recommended next session

Start milestone 1. Keep the goal narrow: refactor main.cpp just enough to expose window state and mouse input, then render the current mouse position on screen. Do not build nodes, levels, or animations yet.
