Detailed development roadmap

Linked List Game

Complete one small task at a time. Each milestone leaves the project in a working state and has a concrete finish line before the next one begins.

Milestones

  1. M01 - Application shell
  2. M02 - Singly linked-list model
  3. M03 - Static diagram rendering
  4. M04 - Draggable nodes
  5. M05 - Pointer rewiring
  6. M06 - Sandbox tools
  7. M07 - First learning level
  8. M08 - Expand from a stable core
M01

Application shell

Create a reliable OpenGL window and one shared coordinate system.

  1. Build the empty executable. Confirm CMake can configure and compile GLFW, GLAD, and the game target.
  2. Move GLFW lifecycle code into Window. Initialize GLFW, create the window, initialize GLAD, and clean up in one owner.
  3. Introduce Application. Give it the main loop: poll events, process input, update, render, and swap buffers.
  4. Add a fixed virtual canvas. Define a 1920x1080 logical coordinate space independent of the physical window size.
  5. Letterbox the canvas. Preserve the 16:9 canvas aspect ratio when the player resizes the window.
  6. Add input state. Track mouse position, mouse buttons, keyboard buttons, and one-frame just-pressed transitions.
  7. Convert physical mouse coordinates. Map the mouse to virtual canvas coordinates and mark whether it is inside the canvas.
  8. Expose a visible diagnostic. Show the logical mouse position in the title bar and log click coordinates during development.
  9. Handle startup failures. Report failed GLFW, window, or GLAD initialization clearly and exit nonzero.

Finish line: the executable opens, resizes with letterboxing, and reports correct 1920x1080 canvas coordinates.

M02

Singly linked-list model

Build a graphics-free, testable data model that safely represents pointer relationships.

  1. Create a stable NodeId. Use an integer handle distinct from a raw memory address.
  2. Define SinglyLinkedList<T>::Node. Store an ID, a generic value, and an optional next ID.
  3. Own nodes inside the list. Store nodes in a container such as std::unordered_map; do not give the renderer ownership.
  4. Add emplaceNode. Allocate an unused ID, construct the payload, and initially set next to null.
  5. Add read-only node access. Allow gameplay and rendering code to inspect a node by ID while preventing accidental direct rewiring.
  6. Add head management. Set or clear the head only after checking that a non-null ID exists.
  7. Add pointer rewiring. Set a node's next to an existing node or null; reject unknown source and destination IDs.
  8. Define deletion behavior. When a node is deleted, clear incoming links and clear the head if it references that node.
  9. Add consistency checking. Verify that head and every non-null next reference a stored node.
  10. Write unit tests. Cover creation, links, null links, deletion, rejected invalid IDs, and a non-integer payload.

Finish line: the list model passes tests without opening an OpenGL window.

M03

Static diagram rendering

Draw a hard-coded list clearly before attempting any interaction.

  1. Add a shader wrapper. Load, compile, link, and report errors for a small colored-primitive shader.
  2. Render one rectangle. Draw a colored rectangle at a virtual-canvas position with a width and height.
  3. Define a visual node layout. Reserve regions for the value, the next label, and the output socket.
  4. Draw a node card. Use rectangles, borders, and simple colors to distinguish node regions.
  5. Add text rendering. Load one font and draw node values, labels, and short status text.
  6. Draw a directional pointer line. Connect one source socket to one destination socket and add an arrowhead.
  7. Draw a null endpoint. Represent a missing pointer with a short line and a visible nullptr label.
  8. Render a fixed three-node example. Show head, nodes A/B/C, two links, and C's null endpoint.
  9. Test different positions. Move the hard-coded cards to ensure links remain readable at varied distances.

Finish line: someone can identify the list order, head, and null endpoint from the picture alone.

M04

Draggable nodes

Let the player rearrange the diagram without changing list data.

  1. Create a view-state record. Store each node's card position separately from the linked-list model.
  2. Implement card hit testing. Determine whether a logical mouse point falls inside a node card rectangle.
  3. Choose the topmost card. If cards overlap, select the card most recently brought to the front.
  4. Begin a drag. On left-button press over a card, remember the selected ID and mouse-to-card offset.
  5. Update the drag. While the button is held, update only the visual position using the stored offset.
  6. End the drag. On release, clear drag state and retain the final position.
  7. Provide visual feedback. Highlight the selected card and keep its links rendered while it moves.
  8. Keep cards visible. Clamp or otherwise recover a card that would be dropped entirely outside the canvas.
  9. Manually test overlap and resizing. Verify dragging works after the window is resized and when cards touch.

Finish line: nodes can be moved freely while all existing pointer lines remain attached to their sockets.

M05

Pointer rewiring

Make pointer editing the central, direct manipulation mechanic.

  1. Define socket geometry. Give every next output a hit area and every node an input target area.
  2. Hit-test the output socket. Start a link drag only when the player presses a valid pointer output.
  3. Store link-drag state. Remember the source node and current mouse position until release or cancellation.
  4. Draw a preview line. Render a temporary line from the source socket to the cursor while dragging.
  5. Find an eligible target. Highlight a node input when the cursor is above it; allow self-links only if the level permits cycles.
  6. Commit a valid drop. On release over a target, call setNext and redraw the persistent link.
  7. Support setting null. On release over empty canvas, set the source next to null.
  8. Reject invalid drops visibly. Keep the old link unchanged and show a brief reason for a disallowed action.
  9. Add undo data. Save the source node's prior pointer before every successful rewire.
  10. Test common rewires. Verify A → B → C can become A → C, A → nullptr, and a cycle when enabled.

Finish line: a player can deliberately create, replace, and clear next links with the mouse.

M06

Sandbox tools

Offer an experiment space where players can build and inspect lists safely.

  1. Add a compact tool panel. Reserve a predictable area for create, delete, reset, undo, and status controls.
  2. Add node creation. Create a node with a default value and place its card at a non-overlapping canvas position.
  3. Add selected-node deletion. Delete a card only after the player selects it; update the model and view state together.
  4. Make reset deterministic. Restore the same small example list and positions every time.
  5. Implement one-step undo. Start with pointer rewires, then add node creation and deletion only after their state snapshots are reliable.
  6. Display structural status. Show head, stored node count, reachable-node count, and whether a cycle is detected.
  7. Explain invalid structure. Flag unreachable nodes or a missing head without silently repairing the player's work.
  8. Try destructive cases. Delete the head, delete a middle node, clear links, and create a cycle; confirm the UI remains stable.

Finish line: a player can freely construct, inspect, break, undo, and reset small singly linked lists.

M07

First learning level: insertion

Turn the sandbox interaction into one guided lesson about a real list operation.

  1. Define a level data shape. Include starting nodes, links, positions, instructions, target graph, and allowed actions.
  2. Create one fixed scenario. Use a three-node singly linked list and one new node to insert after position k.
  3. Explain the goal before editing. State which node should be inserted and where the final link order should end.
  4. Ask the boundary question. Prompt for the valid range of k before the player can change pointers.
  5. Validate the answer. Explain why the first and last valid positions are special; allow a retry after a wrong answer.
  6. Guide the pointer order. Prompt the player to preserve access to the old successor before overwriting a link.
  7. Compare the final graph. Check head, values, and every expected next relationship rather than relying on card positions.
  8. Give specific feedback. Identify the pointer that differs and explain what list segment was disconnected or miswired.
  9. Add level restart. Return to the starting graph and initial card layout with one action.
  10. Playtest with a beginner. Record where they hesitate; simplify wording or feedback before adding another operation.

Finish line: a newcomer can complete one insertion task and articulate why the valid index range matters.

M08

Expand from a stable core

Add scope only when it reuses the established model, interaction, and lesson framework.

  1. Review the first level. Fix unclear controls, bugs, and confusing feedback before introducing new structures.
  2. Add one operation at a time. Prefer traversal, deletion, or reversal as the next focused lesson.
  3. Introduce temporary pointer labels. Add visual labels such as curr, prev, slow, and fast.
  4. Add a doubly linked-list model. Create a dedicated model with prev and next, plus tests for bidirectional invariants.
  5. Reuse pointer interaction. Extend socket definitions instead of creating a separate drag system for every pointer type.
  6. Extract level definitions. Move fixed level data from C++ into versioned data files only after the schema has stabilized.
  7. Add advanced graph-like structures carefully. Support right/down or other slots after single and doubly linked-list lessons are solid.
  8. Add polish last. Improve animation, sounds, themes, accessibility, and scoring only after interactions are trustworthy.
  9. Package a release build. Test the executable on a machine without the development environment before sharing it.

Finish line: every new lesson or data structure extends a proven core instead of bypassing it.
